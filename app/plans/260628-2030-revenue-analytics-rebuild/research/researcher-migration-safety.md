## Current State

### Alembic Migration Conventions

This team uses **handwritten migrations** (not autogenerated). Pattern observed across 11 migrations (refs: 0001 → 0010):

- **Structure:** `upgrade()` and `downgrade()` functions symmetrical
- **FK constraints:** Named explicitly (`fk_<table>_<col>_<ref_table>`); `ondelete` clause always included (CASCADE/RESTRICT/SET NULL)
- **Indexes:** Explicit `op.create_index()` calls; downgrade drops them in reverse order
- **Data migrations:** Handwritten if needed; seed data in `app/seed.py` (IDs 1–8 fixed for test stability)
- **Data backfill:** No examples yet in codebase (new pattern for this migration)

**Key patterns for commission migration:**
- Nullable columns use `nullable=True` with no `server_default`
- Non-nullable columns use `server_default` to bootstrap existing rows
- Unique constraints named with `uq_` prefix
- Composite keys via `primary_key=True` on multiple columns (e.g., `contract_tenants`)

## Proposed Migration Plan (7 Revisions)

### Revision 0011: Create revenue_sources Table + Seed Defaults

**SQL outline:**
```sql
CREATE TABLE revenue_sources (
  id SERIAL PRIMARY KEY,
  host_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name VARCHAR(50) NOT NULL,
  color_hex VARCHAR(7) DEFAULT '#666666',
  is_archived BOOLEAN DEFAULT FALSE,
  created_at DATETIME DEFAULT NOW(),
  updated_at DATETIME DEFAULT NOW(),
  UNIQUE(host_id, name)
);
CREATE INDEX ix_revenue_sources_host_id ON revenue_sources(host_id);

-- Seed default 3 rows per host
INSERT INTO revenue_sources (host_id, name, color_hex)
SELECT DISTINCT host_id, 'Trực tiếp' AS name, '#4CAF50' AS color_hex
FROM reservations
UNION ALL
SELECT DISTINCT host_id, 'Marketplace nội bộ' AS name, '#2196F3'
FROM reservations
UNION ALL
SELECT DISTINCT host_id, 'Khác' AS name, '#9E9E9E'
FROM reservations;
```

**Alembic pattern:**
- Create table with all columns
- Create indexes
- In `upgrade()`, execute raw SQL INSERT for seed via `connection.execute()` (post table creation)
- In `downgrade()`, drop table (cascade)

**Risk:** If host_id is NULL on any reservation, INSERT fails (FK violation). Mitigated by pre-flight check.

### Revision 0012: Add source_id (nullable) to reservations + contracts

**SQL outline:**
```sql
ALTER TABLE reservations ADD COLUMN source_id INTEGER NULLABLE REFERENCES revenue_sources(id) ON DELETE SET NULL;
ALTER TABLE contracts ADD COLUMN source_id INTEGER NULLABLE REFERENCES revenue_sources(id) ON DELETE SET NULL;

CREATE INDEX ix_reservations_source_id ON reservations(source_id);
CREATE INDEX ix_contracts_source_id ON contracts(source_id);
```

**Why nullable initially?** Allows rollback without deleting data. Old `source` column remains as source-of-truth until data migration completes.

### Revision 0013: Data Migration — Map string → source_id

**SQL outline (complex, must be transaction-safe):**
```sql
BEGIN;
  -- For each (host_id, source_string) pair in existing reservations,
  -- find matching revenue_sources.id and populate reservation.source_id
  UPDATE reservations r
  SET source_id = (
    SELECT rs.id FROM revenue_sources rs
    WHERE rs.host_id = r.host_id
    AND rs.name = CASE r.source
      WHEN 'marketplace' THEN 'Marketplace nội bộ'
      WHEN 'direct' THEN 'Trực tiếp'
      WHEN 'manual' THEN 'Khác'
      ELSE 'Khác'
    END
  )
  WHERE r.source_id IS NULL;

  -- Same for contracts
  UPDATE contracts c
  SET source_id = (
    SELECT rs.id FROM revenue_sources rs
    WHERE rs.host_id = c.host_id
    AND rs.name = CASE c.source
      WHEN 'marketplace' THEN 'Marketplace nội bộ'
      WHEN 'direct' THEN 'Trực tiếp'
      WHEN 'manual' THEN 'Khác'
      ELSE 'Khác'
    END
  )
  WHERE c.source_id IS NULL;

  -- Verify all rows were matched
  IF (SELECT COUNT(*) FROM reservations WHERE source_id IS NULL) > 0
    OR (SELECT COUNT(*) FROM contracts WHERE source_id IS NULL) > 0
  THEN
    ROLLBACK;
    RAISE EXCEPTION 'Data migration failed: unmatched source values';
  END IF;
COMMIT;
```

**Alembic pattern:** Use `connection.execute(text(...))` for complex transaction logic. No ORM queries (slower on large datasets).

**Downgrade (optional):** Can be no-op; if needed, NULLIFY source_id columns.

## Rollback Strategy

### Scenario A: Failure during 0011–0012 (before data migration)

**Action:** `alembic downgrade -1` reverses to previous revision. No data loss; both old + new schema coexist safely.

### Scenario B: Failure during 0013 (data migration)

**Risk:** Partial updates (some rows matched, some not). Transaction rolls back automatically if verification fails.

**Remedy:**
1. Fix the CASE logic in 0013 (e.g., new source value discovered)
2. Re-run `alembic upgrade 0013` (idempotent; only UPDATEs rows where source_id IS NULL)

### Scenario C: Failure during 0014–0016 (schema changes post-data migration)

**Action:** Revert to 0013; source_id column stays as nullable FK. App continues using old `source` string column. Retry 0014+ next sprint.

### Scenario D: Failure during 0017 (drop old column)

**Action:** Revert to 0016; old `source` column remains. No data loss. Retry drop in Phase 3.5.

## Recommended Field Placements (Rationale)

### commission_rate, commission_amount

**Placement: reservations + invoices (both tables)**

**Rationale:**
- Reservation = booking fact; may have cancellation/refund that affects final commission
- Invoice = payment fact; actual amount tenant paid determines final commission
- Denormalize (store in both) because:
  - Reservation commission is contractual rate offered to tenant
  - Invoice commission is realized amount (if tenant partially paid)
  - Revenue analytics needs both for reconciliation
- Alternative (single table): denormalized in Invoice only; query Reservation → Invoice for commission chain. Adds O(N) JOIN overhead for "all bookings' commissions" reports.

### monthly_revenue_goal

**Placement: host_profiles (not users)**

**Rationale:**
- 1:1 with HostProfile (via user_id FK)
- KYC-adjacent data (both immutable, set once per quarter)
- Users table should remain lightweight (auth + basic info only)
- HostProfile is already "all host metadata" table (CCCD, bank, payout_schedule)

### source_id (FK to revenue_sources)

**Placement: reservations + contracts (both tables)**

**Rationale:**
- Both have booking/rental source concept (marketplace, direct, manual)
- Contracts = long-term rental; source determines commission tier/strategy
- Reservations = short-term homestay; same source logic
- Separate `revenue_sources` per host because:
  - Host A may label "Marketplace" differently than Host B
  - Admin won't manage sources; hosts do (per-host scope)
  - Colors, renaming, archival are per-host decisions
